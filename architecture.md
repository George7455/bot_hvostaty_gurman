# Архитектура Telegram editorial pipeline

## Назначение

Сервис берёт тему из Google Sheets, генерирует черновик через AI, отправляет конкретную ревизию редакторам, принимает решение через Telegram-кнопки и публикует только одобренный снимок текста.

## Слои

1. `telegram`, `sheets`, `ai` — внешние адаптеры. Они общаются с Telegram, Google Sheets, OpenAI/AI proxy и Telegraph.
2. `planner`, `drafts`, `generation`, `moderation`, `publishing`, `sessions` — прикладные сценарии.
3. `repositories` — вся долговечная работа с PostgreSQL через Prisma.
4. `main.ts` — только сборка зависимостей, запуск и корректная остановка приложения.

Telegram-обработчики не меняют статусы черновиков напрямую. Они проверяют пользователя, разбирают транспортное сообщение и передают действие сервису модерации.

## Плановый поток

```text
09:00 / 15:00 / 21:00 Europe/Moscow
  -> PlannerRun получает DB-lease для временного слота
  -> Sheets ищет первую строку с пустым status
  -> строка определяется неизменяемым content_id, а не номером
  -> ContentPlanItem и строка Sheets получают IN_REVIEW
  -> AI формирует текст
  -> одной DB-транзакцией создаются Draft + DraftRevision(1) + ModerationDelivery
  -> доставка редакторам
  -> кнопочное Telegram-сообщение связывается с revisionId
```

`sheetRowNumber` хранится только как подсказка. Перед обновлением сервис снова ищет `content_id`, поэтому сортировка и вставка строк не меняют целевой материал.

## Модерация и ревизии

Callback остаётся коротким и совместимым с заданием:

- `approve:draftId`
- `rewrite:draftId`
- `rewrite_notes:draftId`

`revisionId` не помещается в callback. Он восстанавливается по паре `telegramChatId + telegramMessageId` из `ModerationMessage`. Поэтому старая кнопка не может одобрить новую версию текста.

Перезапись выполняется сравнением ожидаемой и текущей ревизии внутри транзакции. При успехе создаются новая `DraftRevision`, `ModerationAction` и новая задача доставки.

## Публикация

Одобрение одной транзакцией фиксирует:

- статус `APPROVED`;
- `approvedRevisionId`;
- редактора и время одобрения;
- `PublicationIntent`.

Публикуется текст из одобренной ревизии, а не изменяемое поле сообщения. Для текста длиннее 2200 символов Telegraph-страница создаётся только после одобрения. Готовый анонс и адрес страницы сначала сохраняются в `PublicationIntent`, затем отправляются в канал и копируются в `Publication` как аудит-снимок.

После подтверждённой отправки БД переводит Draft и ContentPlanItem в `PUBLISHED`, затем Sheets обновляется по `content_id`.

## Защита от дублей и восстановление

`PlannerRun`, `ModerationDelivery` и `PublicationIntent` используют DB-lease. Это предотвращает параллельное выполнение одной операции несколькими процессами.

Состояния долговечной операции:

- `PENDING` — готова к выполнению;
- `PROCESSING` — занята процессом до `leaseExpiresAt`;
- `SUCCEEDED` — завершена;
- `FAILED` — подтверждённо не выполнена и может быть повторена;
- `NEEDS_RECONCILIATION` — внешний сервис мог выполнить запрос, поэтому автоматический повтор запрещён до ручной сверки.

Последнее состояние принципиально: после сетевого обрыва Telegram мог принять сообщение, даже если клиент не получил ответ. Автоповтор в такой ситуации создаёт дубликаты.

## Ручная загрузка

`/upload` сохраняет `WAITING_ARTICLE` в `UserSession`. Следующее сообщение или PDF атомарно захватывает сессию через `processingToken`. PDF ограничен 25 МБ, 100 страницами и 60 000 символов извлечённого текста.

Генерация имеет лимит размера, количества AI-вызовов, выходных токенов и общего времени. При недоступности AI система возвращает ошибку и сохраняет исходный материал в сессии для повторной попытки; она не подставляет выдуманный шаблон.

`rewrite_notes` аналогично фиксирует и `draftId`, и `revisionId`, поэтому заметки нельзя применить к уже устаревшей версии.

## Границы доверия

- Разрешены только Telegram user ID из `TELEGRAM_MODERATOR_USER_IDS` и разрешённые чаты.
- Текст темы, статьи, черновика и заметок передаётся AI как недоверенные JSON-данные.
- Пользователю не возвращаются внутренние ошибки и секреты.
- OpenAI-запросы используют `store: false`, таймаут и ограничение выходных токенов.
- Telegraph-аккаунт автоматически не создаётся; используется заранее выданный `TELEGRAPH_ACCESS_TOKEN`.
